# Gateway-microservice (gateway-service)

[![Java Version](https://shields.io)](https://oracle.com)
[![Spring Boot](https://shields.io)](https://spring.io)
[![Spring Cloud](https://shields.io)](https://spring.io)

Центральный API Gateway (Шлюз) всей системы на базе **Spring Cloud Gateway**. Он является единственной внешней точкой входа для всех клиентских запросов (HTTP и WebSockets), отвечает за динамическую маршрутизацию, балансировку нагрузки и сквозную безопасность распределенной архитектуры.

## 🛠️ Стек технологий и особенности

* **Выравнивание экосистемы (Java 21 + Spring Boot 3.4.2):** Микросервис полностью переведен на актуальный стек Java 21 и Spring Cloud 2024.0.0. Это гарантирует 100% совместимость метаданных при динамическом поиске инстансов в Эврике и балансировке трафика к СУБД-микросервисам нового поколения.
* **Реактивная архитектура на Netty:** Сетевой слой функционирует на базе асинхронного неблокирующего движка Netty. Потоки Event Loop (`ctor-http-nio-%d`) циклически распределяют нагрузку по ядрам процессора, обеспечивая максимальную пропускную способность WebSocket-сессий Тетриса.
* **Синхронизация пула (Project Loom):** Включена нативная поддержка виртуальных потоков (`spring.threads.virtual.enabled=true`) для фоновых задач, задач логирования и внутренних планировщиков Spring Boot.

## 🔒 Безопасность и Сквозная Трассировка (Краткое превью)

Шлюз изолирует внутренний контур архитектуры от внешнего мира с помощью кастомного реактивного фильтра аутентификации:

* **Бесшовный WebSocket (Query JWT):** Токен автоматически извлекается как из стандартного HTTP-заголовка (`Authorization: Bearer`), так и из параметров строки запроса (`?token=`). Это решает проблему авторизации долгоживущих WebSocket-соединений из браузерного JavaScript, где отправка кастомных заголовков при инициализации сокета не поддерживается.
* **0% CPU Overhead (Кэширование криптоключа):** Парсинг и генерация секретного ключа `SecretKey` вынесены на этап инициализации бина (`@PostConstruct`). Это полностью исключает повторную ресурсоемкую конвертацию строки секрета через `.getBytes()` при каждом входящем запросе, защищая реактивные потоки Netty от микро-задержек и CPU-pinning'а.
* **Сквозная Трассировка (X-Headers):** После успешной валидации токена шлюз обогащает сетевые пакеты чистыми заголовками `X-User-Id` и `X-User-Name`. Внутренней сети и gRPC-сервисам больше не нужно повторно парсить и валидировать тяжелый JWT.
* **Аудит в реальном времени:** В фильтр внедрена реактивная система логирования, которая выводит трассировочный лог прохождения данных пользователя с указанием его ID, имени и целевого микросервиса. Лог оптимизирован против утечек конфиденциальных данных (тел токенов) при сетевых сбоях.

## 🔬 Глубокий технический разбор AuthenticationFilter

Кастомный компонент `AuthenticationFilter` расширяет `AbstractGatewayFilterFactory` и реализует паттерн **Инлайн-валидации и Обогащения запросов (Token Relay & Request Mutation)**. Фильтр спроектирован с учетом требований асинхронного неблокирующего конвейера Spring WebFlux и сетевого движка Netty.

### 🧠 Архитектурные и оптимизационные решения

1. **Бесшовный гибридный перехват (HTTP + WebSockets)**
   Стандартный браузерный JavaScript (`new WebSocket("url")`) нативно не умеет прокидывать кастомные HTTP-заголовки (например, `Authorization: Bearer`) в момент рукопожатия (Handshake).
   Фильтр решает эту проблему за счет двухфазного поиска токена:
   * Сначала проверяется стандартный заголовок `HttpHeaders.AUTHORIZATION`.
   * Если заголовок отсутствует, фильтр автоматически переключается на парсинг URI Query-параметров: `request.getQueryParams().getFirst("token")`.
     Это гарантирует сквозную бесшовную авторизацию как для административных REST-запросов, так и для долгоживущих игровых WebSocket-сессий Тетриса через единую точку входа.

2. **Оптимизация утилизации CPU (0% Криптографического оверхеда)**
   В базовых реализациях криптографический ключ подписи генерируется при каждом запросе: `Keys.hmacShaKeyFor(secret.getBytes())`. При высоком RPS от игрового движка постоянный вызов метода `.getBytes(StandardCharsets.UTF_8)` и выделение памяти под массив байт вызывают микро-таймауты (Latency Spikes) и пиннинг реактивных потоков Netty.
   * **Решение:** Процесс сборки и валидации `SecretKey` вынесен в жизненный цикл инициализации бина — метод `@PostConstruct`. Ключ собирается ровно **один раз при старте шлюза**, кэшируется в оперативной памяти Java и мгновенно переиспользуется потоками Event Loop без затрат процессорного времени.

3. **Мутация запроса и Сквозная трассировка (X-Headers)**
   Для защиты внутреннего контура системы от избыточных вычислений, шлюз десериализует JWT, валидирует его подпись и производит немутируемую трансформацию реактивного контекста через `ServerWebExchange.mutate()`.
   * Из токена извлекаются ключевые метаданные: `userId` и `claims.getSubject()`.
   * Запрос обогащается чистыми заголовками `X-User-Id` и `X-User-Name` и отправляется по внутренней сети через балансировщик.
     Внутренним микросервисам (на PostgreSQL и MongoDB) больше не нужно подключать тяжелые библиотеки безопасности, знать секретный ключ и тратить CPU на повторный парсинг JWT — они доверяют чистым заголовкам шлюза.

4. **Защита реактивных потоков от I/O-блокировок логгера**
   Стандартный вывод `log.error(..., exception)` при падении валидации JWT автоматически вытягивает из библиотеки `jjwt` полное тело невалидного токена в строковом формате. При DDOS-атаке или сканировании шлюза это приводит к моментальному забиванию дисковой подсистемы и блокировке потоков Netty (`ctor-http-nio-%d`).
   * **Решение:** Уровень логирования ошибок валидации понижен до контролируемого `log.warn`. Вместо стектрейса и тела токена логируется только IP-адрес источника, что сохраняет реактивный сетевой контур полностью неблокирующим и защищает систему от переполнения логов (Log Flooding).

## 🔀 Карта маршрутизации трафика

Шлюз запущен на порту **5555** и перенаправляет запросы по следующим правилам:

1. **USERS-SERVICE (users-auth):**
   * *Тип:* Открытый маршрут (без фильтра JWT).
   * *Назначение:* Точки регистрации, авторизации и базовых операций пользователей (`/login`, `/registration`, `/api/users/**`).
2. **RAGING-HORSE-TETRIS-4-1 (UI статика / tetris-ui):**
   * *Тип:* Открытый HTTP-маршрут (без фильтра JWT).
   * *Назначение:* Раздача статического контента игры (HTML, JS-скрипты, картинки, звуки, а также загрузка скриншотов и фото игроков).
3. **RAGING-HORSE-TETRIS-4-1 (WebSocket / tetris-ws):**
   * *Тип:* Защищенный WebSocket-маршрут (`lb:ws://` под управлением `AuthenticationFilter`).
   * *Назначение:* Активный игровой процесс, обработка сокетов и подключений SockJS (`/game/**`, `/websocket/**`).
4. **MONGO-SERVICE (mongo-service):**
   * *Тип:* Защищенный HTTP-маршрут (`StripPrefix=1` + `AuthenticationFilter`).
   * *Назначение:* Запросы к сервису сохранения дампов игр и скриншотов в СУБД MongoDB GridFS.
5. **GAME-SERVICE (pg-service):**
   * *Тип:* Защищенный HTTP-маршрут (`StripPrefix=1` + `AuthenticationFilter`).
   * *Назначение:* Запросы к сервису статистики и рекордов в СУБД PostgreSQL.

## 🌐 Глобальная CORS Конфигурация

Для бесшовного взаимодействия с фронтенд-клиентами (включая локальные стенды разработки) на шлюзе настроена сквозная CORS-политика:
* Разрешены любые источники (`allowedOriginPatterns=*`)
* Разрешены все HTTP-методы (`allowedMethods=*`) и заголовки (`allowedHeaders=*`)
* Включена обязательная поддержка передачи авторизационных кук и учетных данных (`allowCredentials=true`)

## 🚀 Запуск и Окружение

### Требования
* Установленный JDK 21 (настроенный в переменной окружения `JAVA_HOME`)
* Установленный Maven 3.9+
* Запущенный и активный `Eureka-microservice` на порту 1111

### Порядок запуска
1. Перейти в корневую папку проекта `Gateway-microservice`.
2. Выполнить сборку проекта и очистку артефактов: `mvn clean compile`.
3. Запустить приложение с помощью встроенного плагина Spring Boot.
4. **Рекомендация для диагностики Loom:** При запуске приложения в вашей IDE (например, IntelliJ IDEA) или через JAR рекомендуется передавать JVM-аргумент `-Djdk.tracePinnedThreads=short` в VM Options для контроля отсутствия блокировок несущих потоков операционной системы.
